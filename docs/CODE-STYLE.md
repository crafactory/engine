# Code style and source structure

Use Node 22.12+ and the lockfile-pinned oxlint/oxfmt development dependencies.
`npm run check` runs formatting, lint, structure, inventory, unit tests and the build;
the existing Verify, Android and package workflows inherit these gates where they
already invoke `check`. Do not rely on editor-only formatting.

## Commands

- `npm run format`: apply oxfmt to owned code and configuration.
- `npm run format:check`: reject formatting drift without writing files.
- `npm run lint`: oxlint correctness rules and unused variables in JS/TS/JSX;
  warnings also fail CI.
- `npm run structure:check`: file-length and source placement enforcement.

Oxfmt uses single quotes and normal readable multiline formatting. Import sorting,
package key sorting and embedded-language rewriting are disabled: this change should
not reorder side effects or rewrite fixture strings. Markdown, reference/generated
inventory, Android-generated assets, example plugin fixtures and verbatim notices
are excluded. Lockfiles are ignored by oxfmt itself.
See the [formatter configuration](https://oxc.rs/docs/guide/usage/formatter/config)
and [ignore behavior](https://oxc.rs/docs/guide/usage/formatter/ignore-files).

The initial rollout temporarily lists 140 existing files as exact-path formatting
exclusions. These are adoption debt, not permanent directory exemptions: new files
are checked immediately. Remove the listed paths in subsequent mechanical-format
PRs below the review service's 100-file limit. Lint and structure checks already cover
all owned source, including the temporarily unformatted files.

## File budgets and placement

Owned JS/TS/CSS/Java/HTML source and root tool configurations default to **500 lines**,
including blank/comment lines. The small structure gate covers CSS/Java as well as
JavaScript instead of duplicating two different length policies.
`.source-policy.json` records exact-path legacy ceilings measured at this increment;
these are debt, not a claim that the existing monoliths already meet 500 lines.
Do not raise ceilings to make CI pass. During the remaining mechanical rollout only,
formatting-expanded files may receive an explicitly reviewed post-format ceiling
with a verified behavior-preserving diff, not a simultaneous functional expansion.
After adoption, extract a focused module and reduce/remove
an exception as the corresponding UI or compatibility area is migrated.
The baseline file is reviewed policy, not regenerated by the check command.

New application files belong under existing `src` domains: `compat`, `components`,
`kernel`, `mobile`, `services`, `ui`, or `views`. Existing flat files are explicitly
grandfathered, not a template for new root-level modules. Source paths have at most
five segments, such as `src/components/settings/section/Control.tsx`.
Adding another domain requires an explicit policy change and review.
Use `src/components/ui` for registry shadcn primitives, and domain folders for their
application compositions. Keep native composition/style in `src/mobile`.
See [UI migration and provenance](UI.md).

## Intentional lint boundaries

Compatibility implementations legitimately capture `this` for API callbacks, so
`typescript/no-this-alias` is not enabled. The two Playwright corpus suites require
an empty destructured fixture argument even though they drive Electron; their
`no-empty-pattern` exception is scoped to those suites. Intentional control-character
rejection and unsafe-eval boundary tests have narrow, explained inline exceptions.
Do not enable a broad autofix that removes listener snapshots or changes iteration
semantics merely to satisfy a stylistic preference.
React Compiler migration diagnostics are not enabled as part of this React 18 tooling
increment; changing editor/imperative plugin lifetimes is a separate behavioral change.
