# Plugin compatibility report

Crafactory Engine v0.5.0 provides an experimental independent compatibility subset, not comprehensive Obsidian plugin support. Original code is MIT; dependency licenses remain intact. No proprietary application implementation, SDK package, declaration files or sample-plugin source is used. Public behavioral references and unchanged, external community-plugin release bytes serve different roles: documentation informs original adapters; real plugins are black-box test inputs only. Development and builds now go through a PR; publication waits for completed CodeRabbit review, repaired findings and merge.

## Two explicit runtimes

- **Default Worker:** 27 bounded runtime exports, commands, asynchronous lifecycle, text files, plugin-local JSON and one editor selection. DOM, editor extensions and external CommonJS modules remain rejected. Graceful Worker unload has a two-second force-termination limit.
- **Opt-in trusted renderer:** the same 27 plus 18 bounded UI/render exports, for 45 runtime exports. Select the mode in Community plugins while disabled and approve the separate warning. This mode is NOT sandboxed: plugin source runs on the main renderer and can access DOM, the entire vault bridge and workspace metadata. Main-thread freezes or pathological asynchronous unload cannot be forcibly stopped; completed writes are not rolled back. Do not use untrusted code.

Both modes start disabled, use local `.crafactory/plugins/<id>/manifest.json` and `main.js`, and reset enabled/runtime choices on restart. No automatic `.obsidian` discovery, downloads, marketplace, updates or silent renderer fallback occurs. `script-src` now permits Blob modules for user-authorized source loading, but not `unsafe-eval` or inline script. Electron retains context isolation, sandbox and disabled Node integration. Those platform settings do not isolate trusted renderer plugins from application capabilities.

The [public API index](https://docs.obsidian.md/Reference/TypeScript+API/index) inventory remains 271 names: 154 runtime and 117 type-only. `API-COVERAGE.md` now distinguishes Worker and renderer columns; export availability never establishes every member, overload, timing contract or plugin workflow. `compatibility/member-contracts.json` remains a 12-class Worker baseline, not a renderer or exhaustive member audit.

## New renderer contracts and boundaries

- **Reading processors:** sorted post-processors and named fenced-code processors receive a whole-host sourcePath/frontmatter/docId context. [MarkdownRenderChild](https://docs.obsidian.md/Reference/TypeScript+API/MarkdownRenderChild) subclasses load once and unload after container removal, reading-root replacement or plugin disable; async cleanup is awaited. [Post-processing context](https://docs.obsidian.md/Reference/TypeScript+API/MarkdownPostProcessorContext) section mapping deliberately returns nullable unknown, not fabricated line ranges. This is not reference section partitioning, nested-embed source contexts or Live Preview support.
- **Static Markdown:** [MarkdownRenderer render methods](https://docs.obsidian.md/Reference/TypeScript+API/MarkdownRenderer) append sanitized original Engine Markdown and register owner cleanup. Static rendering deliberately does not invoke plugin processors recursively; reference asset resolution, exact DOM structure, previews, hover and complete lifecycle semantics remain unverified. Late asynchronous whole-host writes target detached roots rather than the replacement note.

- **Cooperative child shutdown:** render-child startup and unload each receive at most one second of grace before owner cleanup proceeds. Ownership is retained until old startup and cleanup actually settle, so a pending child cannot be adopted by a new session. Late Component registrations immediately clean themselves, and canceled startup does not activate nested children. This is an original bounded policy, not reference timing equivalence or forced interruption: arbitrary trusted code can continue side effects, block the main thread or keep promises/resources alive outside registered hooks. Other plugin/Modal/view lifecycle hooks can still hang.

Reloading the same Component waits for its previous startup to settle before resetting disposal state. This prevents a canceled old onload from attaching children to a newer generation. A startup that never settles therefore prevents reloading that same object, but does not block the render owner's bounded shutdown; repeated plugin enable creates a fresh runtime. Exact reference reload and asynchronous hook timing remain uncertified.

Reload also waits for complete prior unload, including its captured cleanup jobs. Unload installs its barrier before invoking user hooks, captures old-generation resources, and invokes the hook, reverse-ordered child unloads and reverse-ordered cleanup callbacks without waiting between invocations. All promises are then awaited together, with the first rejection by invocation order preserved. Thus a pending hook or one pending cleanup cannot delay revocation of other registered DOM events, emitter events or intervals. Async completion order may overlap and is not reference-equivalent timing. Custom asynchronous cleanup and direct trusted-code effects still cannot be forcibly stopped. Disposed Component parents ignore new child admission without unloading supplied objects owned elsewhere.

Each unload revokes already queued load admission, including while another shutdown is pending; later explicit load calls may start a fresh generation after the barriers settle. Joined startup/shutdown failures propagate instead of silently retrying. Auto-started child rejection is observed and parent startup still receives the failed child outcome; removeChild does not unload an unattached supplied object. Repeated public load/unload calls return immediately in the already-loaded/unloaded state, including awaited calls inside the matching hook. Private host lifecycle tracking still waits for actual pending work without introducing public self-dependency. Tests cover those bounded sequences, not arbitrary cross-hook callback cycles.

Stopping a trusted owner immediately revokes processor admission before waiting for its boot promise. Both processor registration methods reject after this transition, including a delayed onload continuation. A native test observes raw reading restored and subsequent reading remaining raw while startup is still pending, then releases startup and verifies both rejections. Arbitrary startup and direct trusted effects still cannot be terminated: vault switching/window close may remain waiting for cooperative owner startup or other hooks. This is not a complete shutdown-liveness guarantee or a sandbox.

Code-block handler throw/rejection restores the original pre node when its replacement container remains attached, then propagates the same error to owner reporting. Two direct registry units assert recovery without relying on host rerender or owner disable. Trusted code that removes or moves nodes arbitrarily is not isolated by this recovery policy.

A revoked post-processor context ignores new addChild requests without unloading the supplied object. Only recorded session-owned children participate in cancellation cleanup, preventing a stale callback from tearing down a child adopted by a successor session. A native transition/command/button test verifies successor event functionality and exactly one final owner cleanup.

- **Settings:** real PluginSettingTab/SettingTab mounting, display/hide, Setting name/description and text, textarea, dropdown, toggle, button and slider controls, with plugin callbacks and existing saveData persistence. The reference lists are [PluginSettingTab](https://docs.obsidian.md/Reference/TypeScript+API/PluginSettingTab), [Setting](https://docs.obsidian.md/Reference/TypeScript+API/Setting), and [TextComponent](https://docs.obsidian.md/Reference/TypeScript+API/TextComponent). Unsupported controls, option listeners and icon buttons still fail; this is not full settings layout/default/validation equivalence.
- **Modal:** original DOM dialog, title/content, open/close callbacks, Escape/outside/close-button handling, keyboard focus cycle and selection-focus restoration. See [Modal documentation](https://docs.obsidian.md/Reference/TypeScript+API/Modal). Scope/keymap integration, stacked-dialog equivalence, mobile animation and complete focus/selection semantics remain unfinished.
- **DOM/status:** a bounded set of HTMLElement creation/text/class/visibility helpers, registered native DOM event cleanup and real status items. Status items currently occupy a separate compact dock above the application status bar, not exact reference placement; all DOM extensions, sanitization and adversarial cleanup remain unaudited.
- **Views:** independently implemented View/ItemView/WorkspaceLeaf classes and registered factories create actual closable plugin panes. See [ItemView](https://docs.obsidian.md/Reference/TypeScript+API/ItemView). These are dedicated overlay panes, not an equivalent workspace leaf tree. `getRightLeaf(false)` and `getLeaf()`/`getLeaf(true)` create a new dedicated pane; split/reuse semantics, menus/actions, resizing, popouts, activeLeaf and Markdown leaves remain unsupported or unverified. Basic get/set state does not reproduce history/layout persistence.
- **CodeMirror:** `registerEditorExtension` applies the host's real extensions via an editor Compartment; mutating a registered extension array and calling `workspace.updateOptions` reconfigures it, following the [registration contract](https://docs.obsidian.md/Reference/TypeScript+API/Plugin/registerEditorExtension). Removal on disable, source/live transitions and StateField/updateListener interoperability are tested with original fixtures. Only the active primary editor receives extensions; secondary split editors, upstream plugins using undocumented editor internals and full Live Preview decorations are not certified.
- **Workspace events:** renderer adds layout-change and editor-change to file-open; editor callbacks observe refreshed snapshots and getViewData reads the active document in reading mode. See [Workspace](https://docs.obsidian.md/Reference/TypeScript+API/Workspace). Selection-only transactions do not emit editor-change, exact reference order/timing and other workspace events are not implemented.

The renderer CommonJS module allowlist contains the installed host packages `@codemirror/state`, `view`, `commands`, `language`, `search`, `autocomplete`, `lang-markdown`, and `@lezer/highlight`. This is not arbitrary npm/Node loading, vendored proprietary modules or reference module-version equivalence. Unknown modules such as `fs` reject explicitly.

## Existing contracts

Plugin/Component retain awaited lifecycle and cleanup, command registration and plugin data; command precedence is editorCheckCallback, editorCallback, checkCallback, callback, with synchronous checking. Custom hotkeys/icon/repeatable/mobileOnly reject. Renderer plugins additionally receive UI hooks: addRibbonIcon, addSettingTab, addStatusBarItem, registerView (with getLeaf/getRightLeaf/getLeavesOfType/detachLeavesOfType/revealLeaf), registerEditorExtension and Markdown processors. Worker mode rejects these without a UI host. Ribbon icons currently use a text-glyph fallback rather than the reference icon set. Public behavior is described in [Plugin](https://docs.obsidian.md/Reference/TypeScript+API/Plugin), [Component](https://docs.obsidian.md/Reference/TypeScript+API/Component), and [Command](https://docs.obsidian.md/Reference/TypeScript+API/Command).

Package metadata is validated before a plugin is offered in Settings: lowercase ids, display names, semantic versions, the optional engine range, an optional caller-supplied relative `.js`/`.mjs` entry (discovery reads the fixed `main.js`), known permission names and service declaration shapes. Declared permissions are enforced by the application host per operation (`vault:read`, `vault:write`, `vault:trash`, `editor:write`, `storage:plugin-data`); manifests without `permissions` keep legacy unrestricted access, and a declared set without `vault:read` receives snapshots without note content or editor text. This is a host-operation check, not a sandbox, and it does not gate command or tab registration.

Vault supports snapshot file identities and allowlisted text read/create/modify/append/copy/createFolder plus rename/trash for files and folder subtrees and a data-URL getResourcePath; options, binary/adapter/delete/process APIs reject. See [Vault](https://docs.obsidian.md/Reference/TypeScript+API/Vault). createFolder now returns the resulting TFolder; create refuses overwrite, appends serialize in-process, writes use optimistic conflicts, and plugin data is isolated by ID, capped at 1 MiB and rejects namespace symlinks. Cross-process/power-loss atomicity and stats equivalence are not certified.

Editor remains a single UTF-16 snapshot selection with asynchronous expected-text-checked writes, not direct reference Editor/CodeMirror internals. Live selections inside hidden frontmatter reject. MetadataCache remains a limited getFirstLinkpathDest resolver, not complete cache offsets/events. Full contracts remain outstanding in [Editor](https://docs.obsidian.md/Reference/TypeScript+API/Editor) and [MetadataCache](https://docs.obsidian.md/Reference/TypeScript+API/MetadataCache). Notice still uses a shared string toast; apiVersion stays `0.0.0`, deliberately not certifying an Obsidian release.

## Real plugins and interpretation

Default Worker still fails all five pinned releases at startup, as recorded in `COMMUNITY-PLUGIN-TESTS.md`. Separate trusted-renderer outcomes and exact bounded workflows are recorded in `TRUSTED-RENDERER-PLUGIN-TESTS.md` and `compatibility/renderer-community-results.json`; the input hashes have not changed.

Reading Time receives positive assertions for document time, settings persistence, editor changes, reading/source transition, selected-text Modal, disable and re-enable. This is not full Reading Time equivalence. Calendar and Advanced Tables startup alone do not certify functional behavior; Dataview and Templater still have first-load blockers. Generic class errors are not guessed API diagnoses. Community stylesheets remain unsupported, and third-party source is never copied into Engine or installer.

Tests in `tests/renderer-contracts.test.ts` cover renderer dispatch/event contracts; `e2e-desktop/renderer.spec.ts` tests actual controls, focus, editor integration, failure cleanup and view/unload. The original Worker export/member/rejection tests remain. Real corpus tests run only with verified external inputs; ordinary CI skips them, while the manual corpus workflow runs both modes. A passing negative test means refusal was observed, not successful compatibility.
