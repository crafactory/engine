# Plugin compatibility report

For the expanded all-time-download top-ten target set, evidence tiers, added
`SuggestModal`/`Scope`/`TextFileView` behavior and remaining native/private-API gaps,
see [Popular-plugin compatibility](POPULAR-PLUGIN-COMPATIBILITY.md). The increment
does not claim full compatibility with all ten plugins.

Crafactory Engine v0.6.0 provides an experimental independent compatibility subset, not comprehensive Obsidian plugin support. Current per-plugin and per-capability status is tracked in [PLUGIN-SUPPORT-MATRIX.md](PLUGIN-SUPPORT-MATRIX.md). Original code is MIT; dependency licenses remain intact. No proprietary application implementation, SDK package, declaration files or sample-plugin source is used. Public behavioral references and unchanged, external community-plugin release bytes serve different roles: documentation informs original adapters; real plugins are black-box test inputs only. Development and builds now go through a PR; publication waits for completed CodeRabbit review, repaired findings and merge.

## Two explicit runtimes

- **Default Worker:** 30 bounded public runtime exports, commands, asynchronous lifecycle, text files, plugin-local JSON and one editor selection. DOM, editor extensions and external CommonJS modules remain rejected. Graceful Worker unload has a two-second force-termination limit.
- **Opt-in trusted renderer:** the same 30 plus 39 bounded public UI/render exports, for 69 public runtime exports. Observed private adapters are not included in that public inventory. Select the mode in Community plugins while disabled and approve the separate warning. This mode is NOT sandboxed: plugin source runs on the main renderer and can access DOM, the entire vault bridge and workspace metadata. Main-thread freezes or pathological asynchronous unload cannot be forcibly stopped; completed writes are not rolled back. Do not use untrusted code.

Both modes start disabled, use local `.crafactory/plugins/<id>/manifest.json` and `main.js`, and reset enabled/runtime choices on restart. No automatic `.obsidian` discovery, downloads, marketplace, updates or silent renderer fallback occurs. The default entry permits Blob modules but not `unsafe-eval`, `wasm-unsafe-eval` or inline script. A separate desktop-only opt-in (`trusted.html`, Community plugins warning + restart) serves a CSP that also permits `unsafe-eval` and `wasm-unsafe-eval`; DataviewJS and `dv.view` require `unsafe-eval`, and Templater requires both for its JavaScript bundle and Rust/WASM parser. No default-entry plugin has a verified WebAssembly-only workflow, so the default entry does not carry the WebAssembly relaxation. The opt-in does not sandbox plugins and is not available in the browser preview. By default Electron retains context isolation, sandbox and disabled Node integration. A separate, explicit profile-wide native opt-in changes those settings after native confirmation and restart; it grants every renderer script filesystem, process, network and credential access, not a per-plugin sandbox. Revocation also requires restart. See [NATIVE-PLUGIN-PERMISSIONS.md](NATIVE-PLUGIN-PERMISSIONS.md) for the authoritative grant, revocation and loader boundaries.

The [public API index](https://docs.obsidian.md/Reference/TypeScript+API/index) inventory remains 271 names: 154 runtime and 117 type-only. `API-COVERAGE.md` now distinguishes Worker and renderer columns; export availability never establishes every member, overload, timing contract or plugin workflow. `compatibility/member-contracts.json` remains a 12-class Worker baseline, not a renderer or exhaustive member audit.

## New renderer contracts and boundaries

- **Reading processors:** sorted post-processors and named fenced-code processors receive a whole-host sourcePath/frontmatter/docId context. [MarkdownRenderChild](https://docs.obsidian.md/Reference/TypeScript+API/MarkdownRenderChild) subclasses load once and unload after container removal, reading-root replacement or plugin disable; async cleanup is awaited. [Post-processing context](https://docs.obsidian.md/Reference/TypeScript+API/MarkdownPostProcessorContext) section mapping deliberately returns nullable unknown, not fabricated line ranges. This is not reference section partitioning, nested-embed source contexts or Live Preview support.
- **Static Markdown:** [MarkdownRenderer render methods](https://docs.obsidian.md/Reference/TypeScript+API/MarkdownRenderer) append sanitized original Engine Markdown and register owner cleanup. Static rendering deliberately does not invoke plugin processors recursively; reference asset resolution, exact DOM structure, previews, hover and complete lifecycle semantics remain unverified. Late asynchronous whole-host writes target detached roots rather than the replacement note.

- **Cooperative child shutdown:** render-child startup and unload each receive at most one second of grace before owner cleanup proceeds. Ownership is retained until old startup and cleanup actually settle, so a pending child cannot be adopted by a new session. Late Component registrations immediately clean themselves, and canceled startup does not activate nested children. This is an original bounded policy, not reference timing equivalence or forced interruption: arbitrary trusted code can continue side effects, block the main thread or keep promises/resources alive outside registered hooks. Other plugin/Modal/view lifecycle hooks can still hang.

Reloading the same Component waits for its previous startup to settle before resetting disposal state. This prevents a canceled old onload from attaching children to a newer generation. A startup that never settles therefore prevents reloading that same object, but does not block the render owner's bounded shutdown; repeated plugin enable creates a fresh runtime. Exact reference reload and asynchronous hook timing remain uncertified.

Reload also waits for complete prior unload, including its captured cleanup jobs. Unload installs its barrier before invoking user hooks, captures old-generation resources, and invokes the hook, reverse-ordered child unloads and reverse-ordered cleanup callbacks without waiting between invocations. All promises are then awaited together, with the first rejection by invocation order preserved. Thus a pending hook or one pending cleanup cannot delay revocation of other registered DOM events, emitter events or intervals. Async completion order may overlap and is not reference-equivalent timing. Custom asynchronous cleanup and direct trusted-code effects still cannot be forcibly stopped. Disposed Component parents ignore new child admission without unloading supplied objects owned elsewhere.

Each unload revokes already queued load admission, including while another shutdown is pending; later explicit load calls may start a fresh generation after the barriers settle. Joined startup/shutdown failures propagate instead of silently retrying. Auto-started child rejection is observed and parent startup still receives the failed child outcome; removeChild does not unload an unattached supplied object. Repeated public load/unload calls return immediately in the already-loaded/unloaded state, including awaited calls inside the matching hook. Private host lifecycle tracking still waits for actual pending work without introducing public self-dependency. Tests cover those bounded sequences, not arbitrary cross-hook callback cycles.

Stopping a trusted owner immediately revokes processor admission before waiting for its boot promise. Both processor registration methods reject after this transition, including a delayed onload continuation. A native test observes raw reading restored and subsequent reading remaining raw while startup is still pending, then releases startup and verifies both rejections. Arbitrary startup and direct trusted effects still cannot be terminated: vault switching/window close may remain waiting for cooperative owner startup or other hooks. This is not a complete shutdown-liveness guarantee or a sandbox.

Code-block handler throw/rejection restores the original pre node when its replacement container remains attached, then propagates the same error to owner reporting. Two direct registry units assert recovery without relying on host rerender or owner disable. Trusted code that removes or moves nodes arbitrarily is not isolated by this recovery policy.

A revoked post-processor context ignores new addChild requests without unloading the supplied object. Only recorded session-owned children participate in cancellation cleanup, preventing a stale callback from tearing down a child adopted by a successor session. A native transition/command/button test verifies successor event functionality and exactly one final owner cleanup.

- **Settings:** real PluginSettingTab/SettingTab mounting, display/hide, Setting name/description and text, textarea, dropdown, toggle, button and slider controls, with plugin callbacks and existing saveData persistence. A bounded declarative renderer also handles `getSettingDefinitions()` groups/pages/items, toggle/dropdown/text/number/folder controls and list add/delete; the pinned Templater corpus verifies text/toggle/dropdown/list add-delete persistence across restart. The reference lists are [PluginSettingTab](https://docs.obsidian.md/Reference/TypeScript+API/PluginSettingTab), [Setting](https://docs.obsidian.md/Reference/TypeScript+API/Setting), and [TextComponent](https://docs.obsidian.md/Reference/TypeScript+API/TextComponent). Settings navigation/search, list reordering, other dangerous-setting flows, unsupported controls, option listeners and icon buttons remain incomplete; this is not full settings layout/default/validation equivalence.
- **Modal:** original DOM dialog, title/content, open/close callbacks, Escape/outside/close-button handling, keyboard focus cycle, selection-focus restoration and ConfirmationModal action buttons that close the dialog. See [Modal documentation](https://docs.obsidian.md/Reference/TypeScript+API/Modal). Scope/keymap integration, stacked-dialog equivalence, mobile animation and complete focus/selection semantics remain unfinished.
- **DOM/status:** bounded HTMLElement/DocumentFragment/SVG creation/text/class helpers, delegated `on`/`off`, insertion/window-migration observers, cross-window `Node.instanceOf`, array endpoints/removal, global element builders, native DOM event cleanup and real status items. Status items occupy a separate compact dock above the application status bar, not exact reference placement. The public [layering variables](https://docs.obsidian.md/Reference/CSS+variables/Foundations/Layers) supply plugin stacking levels; this is not complete theme/DOM/accessibility equivalence.
- **Views:** original View/ItemView/FileView/TextFileView/WorkspaceLeaf classes support main-document registered views and file-specific overrides as well as dedicated overlays. See [ItemView](https://docs.obsidian.md/Reference/TypeScript+API/ItemView). Default `getLeaf()` and `getLeaf(false)` reuse the current main leaf; explicit new-tab requests create leaves. Inactive main tabs retain their views, same-type state updates reuse them, and closing/unloading disposes their resources. File views own real file transitions and TextFileView persistence retains version-conflict protection. Main-view actions and SVG icons are functional. `requestSaveLayout` tracks an actual host write and restores validated host tabs, active/split routes, sidebar visibility and mode, not arbitrary plugin-specific state or an equivalent Obsidian leaf tree. Full history, pane groups, popouts, multiple views of one file, resize behavior and menu equivalence remain incomplete.
- **CodeMirror:** `registerEditorExtension` applies the host's real extensions via an editor Compartment; mutating a registered extension array and calling `workspace.updateOptions` reconfigures it, following the [registration contract](https://docs.obsidian.md/Reference/TypeScript+API/Plugin/registerEditorExtension). Removal on disable, source/live transitions and StateField/updateListener interoperability are tested with original fixtures. Only the active primary editor receives extensions; secondary split editors, upstream plugins using undocumented editor internals and full Live Preview decorations are not certified.
- **Workspace events:** renderer adds layout-change and editor-change to file-open; editor callbacks observe refreshed snapshots and getViewData reads the active document in reading mode. See [Workspace](https://docs.obsidian.md/Reference/TypeScript+API/Workspace). Selection-only transactions do not emit editor-change, exact reference order/timing and other workspace events are not implemented.

The strict renderer CommonJS allowlist contains installed host CodeMirror packages, supported Lezer packages and Moment, not arbitrary npm/Node loading or reference module-version equivalence. Unknown native modules such as `fs` reject in that profile. Only the separate full-trust native profile supplies actual Node/CommonJS loading; it does not complete unsupported Obsidian APIs.

The bounded legacy `window.CodeMirror` registry passes separate editor configuration and mode specification to factories and supports string/object MIME aliases, following the [CodeMirror 5 mode API](https://codemirror.net/5/doc/manual.html#modeapi). Each lookup instantiates its mode independently; unknown modes use an advancing, non-highlighting null mode. This does not implement a full CM5 editor, all modes, helper dispatch or complete overlay semantics.

## Existing contracts

Plugin/Component retain awaited lifecycle and cleanup, command registration and plugin data; command precedence is editorCheckCallback, editorCallback, checkCallback, callback, with synchronous checking. Custom hotkeys/icon/repeatable/mobileOnly reject. Renderer plugins additionally receive UI hooks: addRibbonIcon, addSettingTab, addStatusBarItem, registerView (with getLeaf/getRightLeaf/getLeavesOfType/detachLeavesOfType/revealLeaf), registerExtensions (maps single-segment file extensions to an already-registered view; opening such a file mounts the view in the main document area), registerEditorSuggest (onTrigger/getSuggestions are bridged to CodeMirror autocomplete, selection runs through the editor mutation host, and custom suggestion rendering is limited to the display-text hook), registerObsidianProtocolHandler (dispatched from the in-app `engine:protocol` event; OS `obsidian://` registration is not wired), registerHoverLinkSource (hovering a Markdown link delivers a hover-link event per registered source; the event carries a minimal hoverParent and no hover popover), registerBasesView (renderer-only minimal QueryController with type/config/app; plugins implement `render(container)`; query data/grouping/sorting and full BasesConfig semantics are not implemented), registerEditorExtension and Markdown processors. The renderer emits `file-menu` with a bounded `Menu`/`MenuItem` when the file context menu opens; `files-menu`/`editor-menu`/`url-menu` still reject. `AbstractInputSuggest` and `FuzzySuggestModal` provide input-driven filtering, and `prepareFuzzySearch` returns `{score, matches}`. Worker mode rejects these without a UI host. Ribbon icons currently use a text-glyph fallback rather than the reference icon set. Public behavior is described in [Plugin](https://docs.obsidian.md/Reference/TypeScript+API/Plugin), [Component](https://docs.obsidian.md/Reference/TypeScript+API/Component), and [Command](https://docs.obsidian.md/Reference/TypeScript+API/Command).

Package metadata is validated before a plugin is offered in Settings: lowercase ids, display names, semantic versions, the optional engine range, an optional caller-supplied relative `.js`/`.mjs` entry (discovery reads the fixed `main.js`), known permission names and service declaration shapes. Declared permissions are enforced by the compatibility support service before each host primitive (`vault:read`, `vault:write`, `vault:trash`, `editor:write`, `storage:plugin-data`); manifests without `permissions` keep legacy unrestricted access, and a declared set without `vault:read` receives snapshots without note content or editor text. This is a host-operation check, not a sandbox, and it does not gate command or tab registration.

In-repo extensions add UI through `engine.views/v1` (main/panel component loaders) and `engine.ui/v1` (ribbon buttons, status-bar text, settings sections and opt-in fenced-block previews). Compatibility plugins use the trusted renderer DOM host for ribbon, status, settings tabs, custom views and editor extensions. The compatibility loader is itself the native `engine.compat` runtime plugin (`engine.compat/v1` contract); App resolves it and the **Obsidian plugin support** Core plugin switch gates package loading. Discovery/validation and the permission-to-host operation mapping now live in the support implementation; the Community plugins UI remains application-side. Native `engine.views` UI from arbitrary external plugin packages is not wired yet; the Obsidian compatibility path uses its own DOM host.

Vault supports snapshot file identities, a bounded `FileSystemAdapter`, `getConfig`, allowlisted text read/create/modify/append/copy/createFolder (including `.js`/`.mjs` for custom view scripts), scoped desktop binary operations described below, rename/trash for files and folder subtrees, an advisory collision-free `getAvailablePath` helper (creation still relies on create-only rejection) and a data-URL getResourcePath. Options, general adapter filesystem operations, appendBinary/delete/process still reject. See [Vault](https://docs.obsidian.md/Reference/TypeScript+API/Vault). createFolder returns the resulting TFolder; create refuses overwrite, appends serialize in-process, text writes use optimistic conflicts, and plugin data is isolated by ID, capped at 1 MiB and rejects namespace symlinks. Binary writes do not provide text-version compare-and-swap. Cross-process/power-loss atomicity and stats equivalence are not certified.

Vault now accepts the bounded `create`/`delete`/`rename`/`modify` event registrations; create and delete are derived from snapshot entry diffs, modify from note changes, while rename registration is accepted but no rename event is synthesized. MetadataCache accepts both `resolved` and the reference spelling `resolve`, and emits `resolve` alongside changed for reloaded notes. App exposes the compatibility namespace `appId` (`crafactory-engine`), `isMobile:false`, a bounded `app.plugins.getPlugin`, a synthetic `daily-notes` internal plugin built from the app's daily-note settings, a no-op `foldManager`, JSON-backed `loadLocalStorage`/`saveLocalStorage` and a bounded `fileManager.renameFile` that routes through `Vault.rename`; `workspace.iterateAllLeaves` is supplied by the renderer host. Local storage is renderer-profile state, not a vault file; runtimes without `localStorage` fall back to per-runtime memory, and other App members still reject. The trusted renderer installs `window.app` (owned by the active renderer and released when its owner stops), `moment` as a module export/global/`require`, a production-only `process.env.NODE_ENV` shim for bundled libraries and a minimal `window.CodeMirror` shim (`defineMode`/`getMode`) so plugins that still register CodeMirror 5 highlighting modes can finish startup; highlighting behavior is not emulated. The `process` object is not Node and exposes no filesystem/env mutation.

Editor remains a single UTF-16 snapshot selection with asynchronous expected-text-checked writes, not direct reference Editor/CodeMirror internals. `Editor.getDoc` returns a bounded CodeMirror 5-shaped document view over the same selection and mutation host; it is not a real CM5 `Doc`. `MarkdownView.save` waits for queued editor edits and flushes the active note through a typed host save operation; inactive paths reject. Live selections inside hidden frontmatter reject. MetadataCache provides getFirstLinkpathDest, getFileCache/getCache and changed/deleted/resolved/resolve events. The cache is a bounded CachedMetadata shape derived from note content (frontmatter, headings, links/embeds, tags, sections, listItems, blocks) with full-file line/column/offset positions; the changed event's cache argument remains null. Reference section partitioning, frontmatter-link caches and complete link resolution remain unfinished. fileToLinktext still rejects; resolvedLinks/unresolvedLinks are bounded derived maps from the metadata links plus the host resolver. Full contracts remain outstanding in [Editor](https://docs.obsidian.md/Reference/TypeScript+API/Editor) and [MetadataCache](https://docs.obsidian.md/Reference/TypeScript+API/MetadataCache). Notice still uses a shared string toast; apiVersion stays `0.0.0`, deliberately not certifying an Obsidian release.

## Binary files, styles and native view integration

On desktop, `Vault.readBinary/createBinary/modifyBinary` and `Vault.adapter.readBinary/writeBinary` route through the scoped vault host with the existing read/write grants. They preserve exact typed-array/DataView slices, reject shared buffers and payloads over 64 MiB, and retain protected-path and symlink checks. Create refuses overwrite; modify checks for an existing regular file before staging and checks its identity again before publication. This is not atomic conditional replacement: another process can delete the target after the final check, and rename can recreate it. That reproduced race remains an unresolved PR review finding, not a certified modify-existing guarantee. Browser hosts without binary storage reject explicitly. `appendBinary`, data-write options and arbitrary adapter filesystem methods remain unsupported.

Optional package `styles.css` is read as a bounded, guarded asset and mounted only while the renderer plugin is enabled. Registered views can occupy the main document area via tab leaves and file-specific overrides, instead of being limited to a side overlay. These are host capabilities, not evidence of complete Excalidraw or Kanban compatibility. The bounded private `app.commands` manager currently enumerates and executes the owning plugin's commands only; it does not expose Engine's built-in or other plugins' command registries.

The observed private Markdown embed registry owns real Components and provides a bounded source-editor base/subclass surface with a local editable CodeMirror buffer, Markdown parsing, undo/redo, get/set and document-change hooks. Late initialization reads do not replace an edited buffer, including input subsequently cleared to empty. File persistence remains the owning plugin/view's responsibility. This does not reproduce every private source-editor method or provide popout-window support. Scope/keymap stacks dispatch real key events, and `Component._loaded` reflects host lifecycle state without letting plugins mutate it: redundant assignments are harmless, but attempts to change it reject rather than bypassing load/unload. Obsidian's private core Canvas plugin is still unavailable and its load request explicitly rejects.

Before a host rename or trash operation, file-backed plugin views flush and retire. File-specific overrides are remapped and recreated after rename, or removed after trash, so no retained leaf continues saving through an obsolete file path. Rename does not preserve arbitrary private view state. Reusing a leaf for another file removes the previous explicit path registration; string-backed ItemView files participate in actual active-leaf resolution.

## Real plugins and interpretation

Current per-plugin outcomes and verified workflows are tracked in
[PLUGIN-SUPPORT-MATRIX.md](PLUGIN-SUPPORT-MATRIX.md); per-run hashes and timestamps are in
[TRUSTED-RENDERER-PLUGIN-TESTS.md](TRUSTED-RENDERER-PLUGIN-TESTS.md) and
[compatibility/renderer-community-results.json](compatibility/renderer-community-results.json).
Default Worker still fails all eleven pinned releases. Reading Time and Dataview have bounded
functional workflows; Templater has bounded template-insertion, create-note, startup-template
and user-script workflows; Advanced Tables has a bounded live-mode table-formatting workflow;
Calendar has a bounded view + today's-daily-note workflow. DataviewJS and `dv.view` require the explicit desktop `unsafe-eval`
entry, and Templater also needs `wasm-unsafe-eval` for its Rust/WASM parser. Both capabilities
exist only in the trusted entry. A bounded workflow pass is not full
plugin compatibility, and third-party source is never copied into Engine or its installer.

Tests in `tests/renderer-contracts.test.ts` cover renderer dispatch/event contracts;
`e2e-desktop/renderer.spec.ts` tests actual controls, focus, editor integration, failure cleanup
and view/unload. The original Worker export/member/rejection tests remain. Real corpus tests
run only with verified external inputs; ordinary CI skips them, while the manual corpus
workflow runs both modes. A passing negative test means refusal was observed, not successful
compatibility.
